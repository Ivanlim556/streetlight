Smart Street Light — Sensor-Driven Auto-Dimming

A Raspberry Pi 5 reads local sensors, decides a brightness level from ambient light and presence, and drives a Lumilite street-light controller through its cloud API. This document describes the full system as built and running.

01

Overview

Four sensors wired to the Pi feed a decision engine that sets one output: the lamp's brightness (0–100%). The Pi provides the intelligence — presence detection and ambient-light banding — that the lamp controller cannot do on its own.

4 sensors
Lux, temperature, motion, and mains power, all read locally on the Pi
2 loops
One ingests sensor data; one decides and sends brightness on a timer
4 levels
Brightness bands: 100 / 50 / 30 / 10, chosen by light & motion
MQTT
Sensors and logic communicate over a local Mosquitto broker
02

Architecture

Data flows left to right: sensors → Pi decision engine → vendor cloud → controller → lamp. Inside the Pi, the work splits into two independent loops that meet only through shared memory in Node-RED.

Loop A — Ingest

Sensors publish to MQTT every 2 s. Node-RED routes each topic to the dashboard and to a "Store readings" node that keeps the latest values in flow memory.

Loop B — Decide

A timer fires every 3 s, reads that memory, computes a brightness band, and sends it to the lamp only when the value changes.

The motion heartbeat is important: publishing state every 2 s (not only on PIR edges) keeps the decision loop from getting stuck on a stale "no motion" reading during a long continuous presence.

05

How one cycle works

The two loops run on different clocks — ingest every 2 s, decide every 3 s — and connect only through Node-RED flow memory (lux, motionState, motionEndTime).

  1. Sensors are read by the Python script; values publish to streetlight/1/# over MQTT.
  2. Node-RED's MQTT-in feeds a switch that routes each topic to dashboard widgets and to Store readings.
  3. Store readings saves lux and motionState to flow memory, and stamps motionEndTime the moment motion stops (starts the cooldown clock).
  4. Every 3 s a timer triggers device level, which reads that memory and computes a brightness band.
  5. An rbe filter passes the value on only when it changed, so unchanged levels don't spam the cloud.
  6. send dimTo logs in and POSTs the command; the flow then waits and polls the result back.
  7. The cloud relays it over 4G to the controller, which drives the 0–10V input and the lamp changes brightness.

Plain-language cycle

Someone walks in → PIR HIGH → heartbeat holds motionState = 1 → the 3 s timer evaluates → if dark, 100% → command sent → lamp brightens. They leave → PIR LOW → after a 5 s cooldown, the next evaluation drops it to 10%.

06

Dimming logic

The lamp is considered on while the PIR is high, and for a 5-second cooldown after it drops. When on, the brightness is chosen by ambient light in discrete bands tuned to a room baseline of ~40 lux.

ConditionAmbient luxBrightness
No motion (after 5 s cooldown)any10
Motion · very dark< 10100
Motion · room level10 – 4050
Motion · brighter than room> 4030

Boundary: exactly 40 lux → 50 (room level); 41 and above → 30. Cover the sensor to force full brightness; shine a light on it to drop to 30.

// Node-RED "device level" node
const lightOn = (motionState === 1) || (Date.now() - motionEnd < 5000);

if (!lightOn)      level = 10;    // nobody present
else if (lux < 10)  level = 100;   // very dark
else if (lux <= 40) level = 50;    // room level (~40)
else               level = 30;    // brighter than room
07

Control path to the lamp

The lamp is a 4G device reachable only through the vendor cloud. Each command is one authenticated POST; the brightness command carries the level as a parameter.
