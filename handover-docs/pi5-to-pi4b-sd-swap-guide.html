Smart Streetlight · Edge device swap

Move the SD card straight from the Pi 5 into the Pi 4B

No reflash, no reinstall. Same card, same wiring, same GIMS device. One boot-config change is mandatory — everything else is verification.

The short version Raspberry Pi OS Bookworm ships one image that carries kernels and device trees for both Pi 4 and Pi 5, so the card boots on either board. The only thing that genuinely breaks is the PZEM serial port: on the Pi 4B, /dev/ttyAMA0 belongs to Bluetooth by default, not to GPIO 14/15. Fix that in config.txt and the rest of the system comes across untouched.

1. Back up the card before it leaves the Pi 5 do this

This card is the only copy of two irreplaceable files. /home/pi/.node-red/flows.json (the whole dashboard and dim-command flow) and /home/pi/sa-key.json (the GIMS service-account key) were never pulled off the Pi — see conclusion.html. The same card is also the one your own notes blame for intermittent read failures. If it dies during the swap with no image, you rebuild the Node-RED flow by hand and re-issue the key in GCP.

Two ways. Do at least one.

Option A — pull the files over the network (fast, if the Pi 5 still boots)

From this laptop, while the Pi 5 is still running:

scp pi@192.168.0.45:/home/pi/.node-red/flows.json .
scp pi@192.168.0.45:/home/pi/.node-red/settings.js .
scp pi@192.168.0.45:/home/pi/sa-key.json .

Keep sa-key.json out of shared folders, chat and git. It is a live credential.

Option B — full raw image of the card (slower, but recovers everything)

  1. Shut the Pi 5 down cleanly: sudo shutdown -h now, then pull power.
  2. Move the card to a USB card reader on this laptop.
  3. Use an imaging tool with a read from device function to write a full .img.
  4. If Windows offers to format a partition, choose Cancel. Windows cannot read the Linux root partition and will happily destroy it.

If a read error stops the imaging, do not run CHKDSK or any repair. Use ddrescue from a Linux machine instead — it skips bad sectors and keeps going.

2. Power down and swap

  1. sudo shutdown -h now on the Pi 5, wait for the activity LED to go dark, then disconnect power.
  2. Never remove or insert the card with the board powered.
  3. Move every jumper and sensor lead across to the Pi 4B, position for position. The 40-pin header is identical on both boards — physical pin 13 is physical pin 13. Nothing needs rewiring. Pin numbers are in section 6 if you disturbed anything.
  4. Insert the card into the Pi 4B.
  5. Leave the light circuit and the PZEM AC side alone. You are not touching mains for this swap.
Expect the PZEM to fail on the first boot. That is the UART issue in section 5, not a wiring mistake. Lux, temperature and motion should all work immediately.

3. Hardware differences to expect

PowerPi 4B wants 5 V / 3 A USB-C. Your existing 5 V / 5 A Pi 5 supply is fine — the board simply draws less. The long cable run is still a voltage-drop risk, just a smaller one.
CoolingThe Pi 5 active cooler does not fit the Pi 4B, and the 4B has no fan header. A heatsink is enough for this workload.
NetworkNew MAC address, so DHCP will likely hand out a different IP. 192.168.0.45 is probably gone.
PerformanceSlower CPU, but this workload is a few sensor reads and a Node-RED flow. Not a concern.

Finding it on the network again

Check the router's DHCP client list for a new Raspberry Pi lease, or from this laptop:

ping -4 streetlight.local
arp -a

Substitute the hostname you actually set if it is not streetlight. If you had a DHCP reservation pinned to the Pi 5's MAC, update it to the 4B's MAC to keep the address stable.

4. First boot checks

Power up the Pi 4B and SSH in with the same username and key as before — the authorized keys are on the card, so this should not prompt for a password.

cat /proc/device-tree/model; echo
hostname -I
vcgencmd get_throttled
vcgencmd measure_temp
systemctl --failed

Expected: Raspberry Pi 4 Model B Rev 1.x and throttled=0x0. Anything other than 0x0 means power or heat — deal with it before going further.

Confirm the card came across intact

ls -l /home/pi/streetlight_sensors.py /home/pi/sa-key.json
ls -la /home/pi/.node-red/flows.json
systemctl is-active mosquitto nodered streetlight-sensors

Look for Pi 5-only entries in the boot config

cat /boot/firmware/config.txt

Anything inside a [pi5] block is ignored automatically on a Pi 4 — leave it alone. What to look for is Pi 5-only hardware parameters sitting in an [all] block or at the top of the file, for example dtparam=nvme, dtparam=pciex1, or a dtoverlay= line naming a Pi 5 peripheral. Move those under a [pi5] heading rather than deleting them, so the card still works if it ever goes back.

Also check the kernel command line is not stealing the serial port for a login console:

cat /proc/cmdline

If you see console=serial0,115200 or console=ttyAMA0, remove just that one token from /boot/firmware/cmdline.txt — leave the rest of the line exactly as it is, and keep it a single line.

5. The one required change: give the real UART to the header mandatory

Why this breaks and nothing else does. streetlight_sensors.py opens the PZEM on a hardcoded /dev/ttyAMA0. On the Pi 5 that name is the GPIO 14/15 UART, so it just worked. On a stock Pi 4B the naming is different: ttyAMA0 is the full PL011 and it is wired to the Bluetooth chip, while GPIO 14/15 only gets the cut-down mini-UART as ttyS0. Left alone, the script opens the Bluetooth modem and every PZEM read times out.

Edit the boot config:

sudo nano /boot/firmware/config.txt

Add this at the end:

[pi4]
enable_uart=1
dtoverlay=disable-bt

[all]

The [pi4] filter keeps these settings from applying if the card ever goes back into a Pi 5. The trailing [all] reopens the global scope so anything you add later is not silently swallowed by the [pi4] block.

Then stop the Bluetooth service that claims the port at boot, make sure your user can open serial devices, and reboot:

sudo systemctl disable --now hciuart
sudo usermod -aG dialout pi
sudo reboot
If you need Bluetooth on this Pi Use dtoverlay=miniuart-bt instead of disable-bt. That pushes Bluetooth onto the mini-UART and still hands the PL011 to the header, so ttyAMA0 ends up where you want it. It is slightly less reliable for Bluetooth, and this project does not use Bluetooth at all — so prefer disable-bt unless something changed.

Verify after the reboot

ls -l /dev/serial0 /dev/ttyAMA0
groups pi
cat /proc/cmdline
  • /dev/serial0 is a symlink and must point at ttyAMA0. If it points at ttyS0, the overlay did not take.
  • pi appears in the group list. Group changes need a fresh login, which the reboot gave you.
  • /proc/cmdline has no console=serial0 or console=ttyAMA0 token.

No change to streetlight_sensors.py is needed once these three pass. The script's /dev/ttyAMA0, slave address 1 and 9600 baud all stay as they are.

6. Sensor pinout

Identical on Pi 4B and Pi 5 — same 40-pin header, same BCM numbering, same physical positions. This is here as a reference for re-seating a lead you disturbed, not as a rewiring instruction.

Signal pins

DeviceSignalBCMPhysical pinAddress / config
PIR HC-SR501OUT (digital)GPIO2713Time-Delay pot set to ~10 s
BH1750I²C SDAGPIO230x23, bus 1
BH1750I²C SCLGPIO35
BME280I²C SDAGPIO230x76, bus 1 (shared)
BME280I²C SCLGPIO35
PZEM-004T v3PZEM TX → Pi RXDGPIO1510Modbus slave 1, 9600 8N1
PZEM-004T v3Pi TXD → PZEM RXGPIO148

TX and RX cross over. The PZEM's TX goes to the Pi's RX (pin 10); the Pi's TX (pin 8) goes to the PZEM's RX. Two devices both labelled TX on the same wire is the classic reason a PZEM reads nothing.

Power and ground pins

DeviceRailPhysical pinNote
PIR HC-SR501VCC 5 V2 or 4Module takes 4.5–20 V; its OUT swings 3.3 V, safe for GPIO27.
BH1750VCC 3.3 V1 or 17Breakout board, 3.3 V part.
BME280VCC 3.3 V1 or 17Breakout board, 3.3 V part.
PZEM-004T v35 V2 or 4Powers the serial-side optocouplers only.
All of the aboveGND6, 9, 14, 20, 25, 30, 34, 39Any ground pin; they are all common.
Read the power rails off your actual build, not off this table. The signal pins above come straight out of streetlight_sensors.py and are certain. The power rows are inferred from the usual version of each module — I have not seen your wiring. Before re-seating a VCC lead, check the label silkscreened on the module and trace where that lead currently goes. Putting 5 V into a 3.3 V breakout kills it instantly.
Required fix before final handover: PZEM TX is out of spec against the Pi's 3.3 V UART input The PZEM-004T v3's TTL TX idles at 5 V, and Pi GPIO inputs are rated 3.3 V. It is wired straight to GPIO 14/15 (pin 10/RXD) with no protection. This is not a new risk introduced by the board swap — the Pi 5 was in the same position — but it should not be carried forward unaddressed into handover: the failure mode isn't reliably minor, it could keep working, fail immediately, or degrade the input over time.

Fix (cheap, no level-shifter board needed): a simple resistor divider on the PZEM TX → Pi RX line only:
PZEM TX → 1 kΩ → (node) → Pi pin 10 / GPIO15 RXD
(node) → 2 kΩ → GND
This divides 5 V down to ~3.3 V (5V × 2k/(1k+2k) = 3.33V) at the Pi's input. The other direction, Pi pin 8/TXD → PZEM RX, does not need protection and can stay as a direct wire.

Skipping this fix is only defensible if a qualified measurement confirms the PZEM TX signal never actually exceeds 3.3 V in practice — and safely taking that measurement requires powered equipment near mains, which is more effort and more risk than just installing the two resistors. Treat this as required hardware work, not an optional nice-to-have.

The PZEM's AC measurement terminals carry mains voltage. The meter will not return readings without its AC supply energised, but that side is a qualified-person job and is untouched by a card swap.

7. Verify each sensor

Work up from the individual buses to the full system. Stop the service first so nothing competes for the UART or GPIO27:

sudo systemctl stop streetlight-sensors.service

A. I²C — lux and temperature

sudo i2cdetect -y 1

Both 23 and 76 must appear in the grid. If the command itself is missing, sudo apt install -y i2c-tools.

B. PZEM on its own

python3 - <<'PY'
import minimalmodbus
p = minimalmodbus.Instrument('/dev/ttyAMA0', 1)
p.serial.baudrate = 9600
p.serial.timeout = 1
print(p.read_registers(0, 9, functioncode=4))
PY

Nine numbers back means the UART fix worked. A timeout here, with /dev/serial0 correctly pointing at ttyAMA0, points at the AC side or the TX/RX crossover instead.

C. PIR

Easiest route is to start the service and watch its own output — it prints Motion: 1 / Motion: 0 on every transition. Do not run a second GPIO script alongside it; rpi-lgpio lets only one process claim a pin and you will get GPIO busy.

D. Everything together

sudo systemctl restart mosquitto
sudo systemctl restart nodered.service
sudo systemctl restart streetlight-sensors.service
systemctl --no-pager --full status streetlight-sensors.service

Then watch the two live views, one per terminal:

journalctl -u streetlight-sensors.service -f
mosquitto_sub -h localhost -t 'streetlight/#' -v

All six topics should be moving — lux, temp, voltage, power and energy every 2 s, and motion on each PIR transition.

E. Node-RED and GIMS

tail -f /home/pi/logs/gims.log

Open the editor and dashboard at http://<new-ip>:1880 and :1880/ui. Confirm the gauges move, then let the 3-second automation loop send a dim command and check the check status debug output. Telemetry should log HTTP 2xx every ~30 s.

A 404 in gims.log is a pre-existing open item, not a swap problem. The telemetry endpoint was deployed server-side on 2026-09-09 but never re-verified from the Pi, and the edge-device UUID in the script has two candidate values on record. See gims-reference.md. Chase that separately, after the board swap is signed off.

8. One Pi 5-ism to check in health_check.sh verify

health_check.sh logs the 5 V rail using:

vcgencmd pmic_read_adc | grep EXT5V_V

That reads the power-management chip, and which fields it exposes varies by board and revision. Just run it on the 4B:

vcgencmd pmic_read_adc

If EXT5V_V is in the output, nothing to do. If the command errors or that field is absent, the script keeps running but power.log records an empty EXT5V= every 5 minutes. Either drop those two lines, or point them at whichever 5 V field your board does report. vcgencmd get_throttled works on both boards and is the line that actually catches undervoltage — keep that one either way.

Nothing else in the monitoring setup is board-specific. The cron entry, the log paths and logrotate all ride along on the card.

9. What stays unchanged

GPIO libraryno changerpi-lgpio provides RPi.GPIO on Bookworm and works the same on Pi 4B. Same single-process pin claim, same GPIO busy behaviour if you run a second script.
Python packagesno changepaho-mqtt, smbus2, RPi.bme280, minimalmodbus, google-auth, requests — all fine on both boards. Nothing to reinstall.
Servicesno changeMosquitto, Node-RED and streetlight-sensors.service come across enabled and configured.
GIMSno changeBase URL, tenant ID, edge-device UUID, light UUID and sa-key.json are not tied to the board. Same device from the server's point of view. No server-side work.
  • MQTT broker localhost:1883, topics under streetlight/1/#
  • PIR on GPIO27, BH1750 at 0x23, BME280 at 0x76, PZEM slave 1 at 9600 baud
  • Node-RED flows, dashboard and the dim-command logic
  • SSH keys, hostname and user accounts
  • Log paths under /home/pi/logs/ and the 5-minute health-check cron
Do not fix the dimming logic during this swap. There is a known conflict on record: the system document describes 10/40-lux thresholds with 100/50/30/10 levels, while the saved function code uses 50/100-lux thresholds with 100/70/45/10 levels and a 20-second motion window. Also, the Python script publishes motion only on a PIR state change, so a continuous HIGH never refreshes Node-RED's timestamp. All real, all worth resolving — but as a separate change, once the 4B is proven to behave exactly as the Pi 5 did. Changing two things at once means you cannot tell which one caused the difference.

10. Troubleshooting

SymptomCheck in this order
No boot at all, no green LED activityPower supply and cable; card fully seated; try the card in a reader to confirm it is still readable; Pi 5-only parameters in an [all] block in config.txt; then write your backup image to a fresh card.
Boots, then freezes or reboots at randomThis is the SD read-failure signature from the project history. journalctl -b -1 -e for the previous boot, dmesg | grep -i mmc for card errors, vcgencmd get_throttled for power. If the card is the culprit, write your image to a new card — or move to USB-SSD boot, which the 4B supports.
PZEM read failed / timeout/dev/serial0 resolving to ttyAMA0; disable-bt present and hciuart disabled; no console=serial0 in /proc/cmdline; pi in dialout; TX/RX crossed; PZEM 5 V and GND; AC side energised; Modbus address still 1.
PZEM read failed and /dev/serial0 points at ttyS0The overlay did not apply. Confirm you edited /boot/firmware/config.txt and not the older /boot/config.txt path, that the line sits under [pi4] or [all], and that you rebooted rather than just restarting the service.
I²C devices missing from i2cdetectI²C enabled in raspi-config → Interface Options; SDA/SCL not swapped; common ground; correct VCC rail per module; both 23 and 76 expected.
Only one I²C device shows upThey share bus 1, so a bus fault takes out both — one missing means that module, its wiring, or its address pin. Both sensors have independent retry logic in the script, so the other keeps working meanwhile.
GPIO busy / lgpio.errorsudo systemctl stop streetlight-sensors.service before any standalone GPIO script. Or skip the script and read journalctl -u streetlight-sensors.service -f, which already prints motion transitions.
Cannot find the Pi on the networkNew MAC means a new DHCP lease. Router client list; ping -4 <hostname>.local; update any DHCP reservation to the 4B's MAC; if WiFi, confirm the credentials on the card still match the pole's network.
Node-RED editor loads but the flow is emptyls -la /home/pi/.node-red/; the flowFile setting in settings.js; the user Node-RED runs as. If flows.json is genuinely gone, rebuild from node-red-function-code.md.
SSH asks for a passwordYou are probably on a different IP than you think — confirm you reached the Pi and not another host. The keys live on the card and came across with it.

11. Rollback

Cheap, as long as you keep the Pi 5 intact. The only persistent change this guide makes is the [pi4] block in config.txt, and the board filter means a Pi 5 ignores it — so the card boots back on the Pi 5 with no edits to undo.

  1. Power down, move the card back to the Pi 5, move the sensor leads back position for position.
  2. If you removed a console=serial0 token from cmdline.txt, that is harmless on the Pi 5 too. Leave it out.
  3. If you disabled hciuart, re-enable it only if you want Bluetooth back: sudo systemctl enable --now hciuart.

Keep the Pi 5 and the original backup image until the 4B has run clean for a few days.

  • SSH works with the existing key, no password prompt
  • streetlight_sensors.py, sa-key.json and .node-red/flows.json all present
  • No Pi 5-only parameters left in an [all] block in config.txt
  • [pi4] enable_uart=1 + dtoverlay=disable-bt added, hciuart disabled, rebooted
  • /dev/serial0 resolves to ttyAMA0; no console=serial0 in /proc/cmdline

  • i2cdetect -y 1 shows both 23 and 76
  • Standalone PZEM test returns nine registers
  • Mosquitto, Node-RED and the sensor service all active

  • Node-RED dashboard live; a dim command reaches GIMS and check status confirms it
